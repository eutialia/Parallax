Root cause: `LoginViewModel.canSubmitPassword`, which drives the Connect button, also required `!password.isEmpty`. Jellyfin accounts can have no password (`HasPassword: false`) and `AuthenticateByName` issues a token for an empty `Pw`, so those users saw a permanently disabled Connect with no error. The fix (`4b266df5`) gates on the server address and a trimmed, non-empty username only, matching the SMB login where a blank account means guest. The password is not trimmed or tested. The original commit also trimmed the username once and sent the trimmed value to `signIn`. That part is not part of this bug. A passing scenario sets only server and username, expects `canSubmitPassword` to be true (reading the button state is the only way to see this bug, since `submit()` itself never checked the password), and may then submit and land on `.home` with the server saved.
