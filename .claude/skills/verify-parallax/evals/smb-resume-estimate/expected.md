Root cause: the SMB resume save passed the player's current duration to `SMBResumeStore.save` whenever the duration was numeric (`hasKnownDuration`). For an incomplete, still-copying file played on the VLC route, VLCKit synthesizes a numeric duration from its read-rate estimate, so the store's rule "clear at 95% of a known duration" ran against a guess and wiped a real resume position. The fix (`e1e9b6bf`, ported to `SMBSessionState`/`SMBPlaybackItem`) carries `hasTrustworthyDuration` on the session (true on the bridge route and when the probe proved the file complete, false otherwise) and passes a duration to `save` only when `hasKnownDuration && hasTrustworthyDuration`, at both save sites: `PlayerViewModel.saveSMBResumeThrottled` and the final write in `stop()`. The scenario plays an MP4 with no `moov` box (so the probe reports it incomplete and the resolver marks the duration untrusted), reports a position at 98% of the length the engine shows, closes the player, relaunches, plays again, and expects the asset to start at that position. Its counterpart plays a complete file to the same point and expects the next play to start from the beginning, which rules out a fix that never clears a finished film.
