Root cause: `JellyfinResponseValidator` treated every HTTP 401 as Jellyfin rejecting the access token. It reported the rejection, which signed the server out, deleted the working Keychain token and routed the user to a sign-in that the gateway would also 401. A 401 from an auth gateway in front of Jellyfin (Authelia, Authentik, a basic-auth reverse proxy) is the gateway's own challenge, and the Jellyfin token is untouched. The fix (`16749b40`, gateway-401 half only) checks for a `WWW-Authenticate` header on the 401. RFC 7235 requires it on a challenge, and Jellyfin's own token rejection sends none. When it is present the validator throws a plain `AppError.server(statusCode: 401, message: nil)` and does not call `onTokenRejected`, so the session and token survive. The scenario puts a `FakeJellyfinServer` behind a gateway via the seam in `setup.patch` (`putBehindGateway()` answers every request 401 with `WWW-Authenticate: Basic`), reloads Home, and expects the server still listed as signed in, the router still on `.home`, and shelves loading again after `clearGateway()`. A bare 401 from the fake server must still sign the user out (the revoked-token scenario covers that). A solution that ignores the header and never signs out on a 401 breaks that scenario. The setup seam changes only `FakeJellyfinServer.swift`.
